<Chapter label="The question" title="Is Java too heavy for serverless?" lede="Cloud Run bills for memory and scales to zero, so the runtime is a line on the invoice, and the cold start is the first thing a customer feels after a quiet hour. ‘Java is too heavy for serverless’ gets said a lot and measured rarely. So I built the same portal three times and measured each one.">
<List>
  <Item title="Change the runtime, nothing else.">The same pages, the same Datastore kinds and the same features in all three. Otherwise the comparison measures the rewrite, not the runtime.</Item>
  <Item title="Data stays compatible.">Bank details written by the Spring Boot version stay readable by Helidon, and a startup check decrypts a seeded record to prove it.</Item>
  <Item title="Server-rendered throughout.">Forms and tables don't need a client framework, and server rendering keeps CORS, bearer tokens and client-side routes off the attack surface.</Item>
</List>
</Chapter>

<Chapter label="Security" title="Safe enough for money and bank details." lede="The customer never sees most of this, and shouldn't have to. All three builds do the same.">
<List>
  <Item title="Bank details encrypted at rest.">AES-256-GCM, with only the last four digits of the account and the last two of the sort code kept readable.</Item>
  <Item title="Limits per caller.">Five sign-ins every 15 minutes, three payments an hour and 60 requests a minute. Five wrong sign-ins lock the account for 30 minutes.</Item>
  <Item title="Headers on every page.">A content security policy with a fresh nonce per request, HSTS, frame denial and CSRF tokens on every form.</Item>
  <Item title="An audit trail.">Payments, contact changes and bank detail updates are logged to Firestore.</Item>
</List>
</Chapter>

<Chapter label="The limits" title="Where each build stops." lede="Each limit is a known trade, with the next step already named.">
<List>
  <Item title="Helidon keeps sessions in memory.">Simple and free, but it pins the service to one instance with session affinity. Go's encrypted cookies show the way out.</Item>
  <Item title="1.3 seconds needs the CPU boost.">If a service level demanded sub-second cold starts without it, the native build would come back.</Item>
  <Item title="Go isn't measured yet.">Its figures go through the same scripts before they're quoted.</Item>
</List>
</Chapter>

<Chapter label="The learning" title="What carried forward." lede="Lessons from building the same thing three times.">
<Split>
<List>
  <Item title="Parity is the method.">Freeze everything except the thing you're comparing, or the numbers measure the rewrite.</Item>
  <Item title="Measure before you replace.">Helidon kept the standard SDKs and only hand-wrote what was missing, after measuring what each cost.</Item>
  <Item title="Fewer parts, fewer surprises.">Go needed two libraries. Spring Boot needed a quarter-hour native build to start quickly.</Item>
  <Item title="A release routine I'd hand to any team.">Deploy to a revision with no traffic, run an idempotent seed job, pass a health check, then take traffic. A bad build never meets a customer.</Item>
</List>
