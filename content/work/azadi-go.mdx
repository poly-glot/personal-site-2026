<Chapter label="Strategy" title="Let customers manage their agreement themselves, whenever something needs doing." lede="Every page on that board serves someone who already has a finance agreement on an Azadi car. They come when something needs doing, such as a payment, a new bank account or paying off early, and then not again for months. So the portal has two jobs. It has to let them finish the task themselves the moment they need to, and it has to cost Azadi next to nothing in the months between." split>
<Split reverse>
<Steps>
  <Step open name="The aim" hint="customers sort it out themselves">Winning means a customer who needs to pay, settle early or change their bank details does it in the portal in a few minutes, at any hour, and never has to phone. Azadi&apos;s phone lines are then left for the questions that need a person.</Step>
  <Step name="Where to play" hint="existing agreements only">The portal is for people who already have an agreement with Azadi Financial Services, and the list of what it leaves out is written down. It offers no new finance, no quotes, no applications and no way to change the car. Leaving those out keeps every page about the agreement the customer already has.</Step>
  <Step name="How to win" hint="nothing to remember">A customer who visits a few times a year will not remember a password. So logging in takes three things they already have, their agreement number, date of birth and postcode, and after that every task is one menu away. Each visit has to work without help, because a customer who comes a few times a year never gets the chance to learn the portal.</Step>
  <Step name="What it takes" hint="safe with money, and pennies to run">The portal takes card payments and stores bank details, so it has to keep both safe. It also sits idle most of the time, so it has to be cheap to run. The brief treats cost as a requirement in the same way as safety, which meant the runtime underneath the portal had to be chosen by measuring it.</Step>
  <Step name="How we'd know" hint="something to measure for each">Each bet gets something to measure. Calls replaced and tasks finished online would show whether customers sort things out themselves, though Azadi is imaginary, so there are no calls or customers to count. Pence per busy hour, an hour in which the portal serves the whole time, would show the cost of running it, and the seconds a customer waits after a quiet spell would show whether the portal is ready when they arrive. Those two are measured on the live portal.</Step>
</Steps>

<Chapter label="Security" title="The same checks stand between every request and the money." lede="Two of those nine pages handle money directly. Make a Payment takes card payments through Stripe, and Update Bank Details changes the account that payments are taken from. The brief asked for the portal to be safe with both, so every request passes the checks drawn below before it reaches a page. All three builds make exactly the same checks, which keeps the runtime comparison that follows fair.">
<AzadiRequestGuard />
<List>
  <Item title="Card numbers never reach the portal.">The customer types their card into Stripe&apos;s own field, which sends it straight to Stripe. A payment counts only when Stripe confirms it with a signed message back to the portal.</Item>
  <Item title="Bank details are encrypted before they are stored.">The customer ticks three confirmation boxes first. The details are then encrypted with AES-256-GCM, and only the last four digits of the account number and the last two of the sort code stay readable.</Item>
  <Item title="Wrong guesses lock the login.">Five wrong tries lock that agreement for 30 minutes. Each caller also gets five logins every 15 minutes, three payments an hour and 60 requests a minute.</Item>
  <Item title="Every change leaves a record.">Payments, changes to contact details and changes to bank details are all written to an audit trail.</Item>
</List>
</Chapter>

<Chapter label="The runtime" title="Go starts fastest, and Cloud Run charges more for time than for memory." lede="Safety was the same in every build, so the brief&apos;s other requirement, a low running cost, decided the runtime. A common view is that Java is too heavy for Cloud Run, Google&apos;s service that runs a server only while it has work and bills by the second. I treated that as a hypothesis to test. I built the portal in Spring Boot, then Helidon, then Go, and kept the pages, the data and the checks the same. Each build is a working portal by itself, live in London.">
<AzadiRuntimes />
<AzadiHourCost />
<List>
  <Item title="Memory is the cheap part of the bill.">The Java builds use 75 and 104 MiB against Go&apos;s 8, so the hypothesis is right about memory. Spring Boot gets that low only as a native image, compiled ahead of time into one program; on a full Java runtime it held 441 MB in an earlier lab test. But a second of a gigabyte of memory costs about a tenth of a second of one processor, so memory is 9% of Spring Boot&apos;s hourly price and 5% of the others&apos;.</Item>
  <Item title="Time is the expensive part.">Cloud Run bills the processor for every second an instance, one running copy of the server, spends starting or serving. Go is ready in under a second and the Java builds take about three, so once the wait drawn further down is gone, Go will be billed for about 2.3 to 2.6 fewer seconds each start. That is a fraction of a penny; the customer&apos;s wait matters far more than the bill. For a busy hour, Go and Helidon cost £0.096 and Spring Boot £0.100.</Item>
  <Item title="At today&apos;s traffic, all three cost pennies.">Over the last 30 days each build was billed for between 65 and 76 minutes, worth 10p to 13p at list price, and Helidon&apos;s was lowest by a penny. A month at demonstration traffic is too small to separate them, so the comparisons that matter are the busy hour and the seconds each start costs.</Item>
  <Item title="Go runs the portal now.">It costs no more than the others in a busy hour, and it starts fastest. Its image, the package a server downloads before it starts, is 16 MiB against 93 and 118. It needs two libraries beyond the language, and a push reaches the live site in about 8 minutes, half Spring Boot&apos;s time and a little slower than Helidon.</Item>
</List>
</Chapter>

<Chapter label="The cold start" title="After a quiet spell, every build makes a customer wait 5 seconds." lede="Starting in under a second should give Go the quickest first page, but the drawing shows it does not yet. When nobody has visited for a while, Cloud Run stops every instance, and the next customer waits while a new one starts. That is a cold start. Cloud Run sends the customer in only once a health check passes, a test request asking the server whether it is ready. Ours waits 5 seconds before its first try. So the first page takes 5.0 seconds on all three builds.">
<AzadiColdStart />
<List>
  <Item title="The wait comes from the infrastructure settings.">Every service is set up by the same shared infrastructure code, which tells the health check to wait 5 seconds and then try every 10. Go is ready after 0.65 seconds and spends the other 4.3 waiting.</Item>
  <Item title="The fix is the next saving.">Starting the check straight away and trying every second would let each build take the customer as soon as it is ready. That is where Go&apos;s quick start would finally reach the customer and the bill. It is a change to the infrastructure, and it is not applied yet.</Item>
</List>
</Chapter>

<Chapter label="The build" title="A new version takes customers only after it passes its checks." lede="That fix reached customers the way every change does. A push to the main branch runs the steps drawn below. The new version, a revision in Cloud Run&apos;s words, starts beside the old one and takes no customers until its health check passes. If any step fails, the release stops there, and customers stay on the version they already had. One of those steps runs 231 test functions with Go&apos;s race detector, which catches two parts of the code changing the same data at once.">

<Chapter label="The limits" title="Where the strategy is not proven yet." lede="The release routine keeps a broken version away from customers, but some gaps sit in the design itself. Each one below is set against the part of the strategy it puts at risk. The one a customer meets first is the 5-second wait after a quiet spell, and the one that would matter most if traffic grew is where a customer&apos;s session is kept.">
<List>
  <Item title="How to win: a customer waits 5 seconds after a quiet spell.">The health check&apos;s first try comes 5 seconds after an instance starts, so the first page after a quiet spell takes 5 seconds on every build. The fix, starting the check straight away, is named and not applied.</Item>
  <Item title="What it takes: a second instance would log customers out.">In all three builds the cookie holds only an encrypted session ID, and the session itself lives in the memory of the instance that made it. It ends after 15 minutes idle. Helidon is pinned to one instance for that reason. Spring Boot and Go may run up to 10, and a customer whose next request reached a new one would be logged out. Today&apos;s traffic never starts a second. The next step is to keep the session itself in the encrypted cookie, or to pin every build to one instance.</Item>
  <Item title="What it takes: login limits are counted by each instance.">For the same reason, the lockout after five wrong tries and the limits per caller are kept in each instance&apos;s memory. Two instances would each keep their own count, and every count starts again from zero when Cloud Run stops an instance after a quiet spell.</Item>
  <Item title="How to win: the date of birth boxes have no names for screen readers.">The day, month and year boxes on the login page share one label, so a screen reader announces three unnamed lists. It is the one point Lighthouse marks down, and the fix is a hidden label on each box.</Item>
  <Item title="The aim: a mistyped address gets plain text.">An unknown address returns the words ‘404 page not found’ and nothing else, with no menu and no link back to My Account.</Item>
</List>
</Chapter>

<Chapter label="The lessons" title="Three things I would do the same way again." lede="The strategy asked for a portal that customers can use by themselves, that is safe with their money and that costs very little to run. The limits above are what is left to close. These three choices did most of the work behind the rest, and I would make them again.">
<Split>
<List>
  <Item title="Test a common belief before acting on it.">The usual case against Java is memory. On the live bill, memory was 5 to 9% of an hour&apos;s price, and the next real saving turned out to be the health check&apos;s wait, which changing the runtime alone would never have found.</Item>
  <Item title="Change one thing at a time.">All three builds share the same pages, the same data and the same checks, and bank details saved by one build can be read by the others. Their Cloud Run settings differ, Spring Boot with 1 GiB and Helidon held to one instance, so the sheet shows those settings beside the numbers.</Item>
  <Item title="Make every step worth having by itself.">Each build is a whole portal, live at its own address. If the experiment had stopped after any one of them, Azadi would still have had a working portal.</Item>
</List>
