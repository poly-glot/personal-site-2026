<Chapter label="The gate" title="Every message passes one gate." lede="Each of those sends, from the console or the API, goes through one gateway, the only code that hands a text to AWS, after a send policy of seven checks has said yes. One setting picks the gateway's mode. That keeps the code that spends money, and the switch from a laptop to production, in one place.">
<Split>
<Facts>
  <Fact k="Fake">Sends nothing. The gateway reports every text delivered, unless the number ends 00 to 03, which fail as invalid, unreachable, blocked or spam. The live site runs this mode.</Fact>
  <Fact k="Dry run">AWS checks the request and stops, so a developer can test the real path and nobody receives or pays for a text.</Fact>
  <Fact k="Sandbox">Real texts, but only to the account's own verified numbers, under AWS's cap of US$1.00 a month.</Fact>
  <Fact k="Live">Real texts to anyone the policy allows, once AWS grants production access.</Fact>
</Facts>
<Facts>
  <Fact k="Country">Refuses a country the account hasn't enabled. The default list holds GB alone.</Fact>
  <Fact k="Opt-out">Refuses a number that has opted out.</Fact>
  <Fact k="Trial">Refuses once the 14-day trial ends without a top-up.</Fact>
  <Fact k="Balance">Refuses a send that costs more than the balance, and names both amounts.</Fact>
  <Fact k="Daily cap">Refuses the 501st message of the day, under the default cap of 500.</Fact>
  <Fact k="Sender">Refuses a sender ID, the brand name or number a text comes from, that isn't ready for that country.</Fact>
  <Fact k="Verified">In sandbox mode, refuses a number the account hasn't verified.</Fact>
</Facts>
</Split>
<List>
  <Item title="Fake mode refuses the same sends as live.">The policy runs in fake mode too, in the order above, and a test checks each refusal's wording letter for letter.</Item>
  <Item title="A price ceiling on each call.">Each request to AWS carries a maximum price, US$0.10 by default, so a text that would cost more fails on its own instead of running up the AWS bill.</Item>

<Chapter label="The money" title="Count money in millionths of a pound." lede="The balance check in that policy compares two amounts, and a UK text costs £0.0427, a sum pence can't hold. I stored every amount as a whole number of micro-pounds, millionths of a pound, and kept floating-point numbers, which round, away from balances, quotes and rates.">
<Facts>
  <Fact k="Units">£0.0427 is 42,700 and the £2 trial credit is 2,000,000. Stripe works in pence, and the code converts at that one boundary.</Fact>
  <Fact k="One owner">Only the billing part of the code changes a balance.</Fact>
  <Fact k="The debit">One transaction in DynamoDB, Amazon's database, holds two writes that succeed or fail together. It takes the money if the balance still covers it, and adds a row to the ledger, the record of each change to the balance, if that row is new.</Fact>
  <Fact k="Reserve, then settle">Confirming a send reserves the full quote. When the last recipient is accounted for, the campaign keeps the cost of what AWS accepted and refunds the rest with a refund row.</Fact>
  <Fact k="Failed texts">The campaign bills a text AWS accepted even if it later fails, because AWS bills the platform the same way. A text AWS never accepted goes back to the balance.</Fact>
  <Fact k="The ledger">Rows are only ever added, so reading one account's rows rebuilds its balance.</Fact>
  <Fact k="Both sides">Tests sit on each side of a limit: a balance equal to the quote sends, the policy refuses a balance one micro-pound short, and the 500th send of the day goes while the 501st stops.</Fact>
</Facts>
</Chapter>

<Chapter label="The retries" title="Send each text once, even on a retry." lede="A reserved balance stays right only if each text goes once. The queue feeding the send worker, a small function on AWS Lambda, can deliver a job twice, and AWS has no way to mark a send as a repeat. The worker writes a claim to DynamoDB before calling the gateway, so a repeated job finds the claim and stops.">
<SendGate />
<Facts>
  <Fact k="Claim the row">In one transaction, the worker writes the message row as queued and a marker for that send and number, on the condition that no marker exists yet. If one exists, the job is a repeat.</Fact>
  <Fact k="Check again">The worker checks the opt-out list and the daily cap again, because time has passed since the customer confirmed.</Fact>
  <Fact k="Claim the attempt">One conditional update, a write that applies only if the row still matches, stamps the row as attempted if it is still queued and unattempted. The worker calls the gateway after that, and marks the row sent.</Fact>
  <Fact k="After a crash">A row with no attempt stamp that is at least 60 seconds old resumes. A row with a stamp never sends again, because AWS may already have it. A crash at that moment loses the text instead, and the sweep for stuck campaigns refunds it.</Fact>
  <Fact k="Late reports">Each send carries its row's key, so a delivery report updates the row in one write. A late Sent can't overwrite Delivered, and a repeated report changes nothing.</Fact>
  <Fact k="One bad job">The worker reports failures message by message, so one bad job doesn't resend the nine that worked. After three failed tries a job moves to a dead-letter queue, a holding queue for failed jobs.</Fact>
  <Fact k="Stuck campaigns">The scheduler settles a campaign with no progress for an hour and refunds the texts that never went out.</Fact>
  <Fact k="Proof">Tests run the same job twice and see one call to the gateway, and check that a 60-second claim resumes while a 59-second one doesn't. The spec allowed one duplicate after a crash; the code is stricter, and a test holds it there.</Fact>
</Facts>
</Chapter>

<Chapter label="The limits" title="Where it stops today." lede="The claim before each send and the ledger both run against the fake carrier on the live site, and that is the first limit. The code and its specs show the other three.">
<List>
  <Item title="No real text leaves the live site.">The deployment runs the fake carrier and takes payments through a Stripe sandbox, Stripe's test mode, so it sends no text and charges no card. Live sending needs production access from AWS, a raised spend quota and a country block set at AWS.</Item>
  <Item title="About five messages a second.">The send worker runs two copies at once on a table it shares with two other apps. The spec works that out at about five messages a second, or half an hour for 10,000. The spec's next step is a table of its own and more copies of the worker.</Item>
  <Item title="No emails go out.">The code can send low-balance and invitation emails through Amazon SES, Amazon's email service, but the deployment sets no sender address, so it logs a line in place of each email.</Item>
  <Item title="A ledger note can drift.">Each ledger row also notes the balance after it, worked out from a read before the transaction. Two debits at the same moment can leave that note off by the other's amount, while the account's balance stays exact.</Item>
</List>
</Chapter>
