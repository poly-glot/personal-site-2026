  <Row title="Find a product by its code">Search takes a keyword or a SKU, the stock code printed on each product, such as BX-CL220.</Row>
  <Row title="Order on trade terms">The trade order form asks for a company name and a delivery postcode, with room for a purchase order reference if the buyer's accounts team needs one. It never asks for a card.</Row>

<Chapter label="The trade maths" title="The same price rule runs in two places." lede="The basket shows the right pack price as the buyer types a quantity, so the rule has to run in the browser. Anyone can change the numbers in their own browser, though, so the server works the order out again from its own data before it stores anything.">
<Facts>
  <Fact k="Three prices">Each of the 32 products has three price breaks, the pack counts where a cheaper price starts. The first starts at 1 pack and matches the headline price. Half the range gets cheaper at 4 and 12 packs, the other half at 5 and 10.</Fact>
  <Fact k="Best price">The top price break saves 16.1% to 22.3% on the single-pack price, and 18.1% on average.</Fact>
  <Fact k="The rule">Of the price breaks the quantity has reached, use the one with the most packs. The browser's `activeTier` in JavaScript and the server's `boxes_unit_price` in PHP both apply that rule.</Fact>
  <Fact k="Delivery and VAT">Delivery is £7.95 unless the subtotal is £150 or more. VAT is 20% of the subtotal plus delivery. Both sides round each line, the subtotal, the VAT and the total to the penny, in the same order.</Fact>
  <Fact k="Worked example">12 packs at £24.50 make £294.00. Delivery is free, VAT is £58.80 and the total is £352.80. The server's code, with the delivery and VAT figures the seed stores, works out the same four figures.</Fact>
  <Fact k="What the server trusts">The browser sends only the SKU and the number of packs for each line. The server looks up each price itself, caps each line at 999 packs as the browser does, and drops any line below 1.</Fact>
</Facts>
</Chapter>

<Chapter label="The basket" title="A basket without a shop plugin." lede="The usual way to keep a basket and an order on WordPress is a shop plugin such as WooCommerce, and I left it out. Firebase Hosting, which serves the public address, passes only one cookie through to WordPress, so it would drop the plugin's basket cookie between pages.">
<Facts>
  <Fact k="Products">A WordPress content type of their own, `product`, defined in a YAML settings file. An editor changes prices in a list called Bulk discounts, one row per price break.</Fact>
  <Fact k="Add to basket">A plain form that points at the basket page with the SKU and quantity, so without JavaScript it still opens the basket page, which says how to order by phone or email instead. With JavaScript, a 9,903-byte script saves the line in the browser's own storage and announces it to screen readers. The server holds nothing until the buyer places the order.</Fact>
  <Fact k="Basket prices">The script reads them from one data file, `/assets/search-index.json`, which the theme builds from the product records. Search reads the same file.</Fact>
  <Fact k="Placing the order">The script copies the lines into a hidden field. The server checks a WordPress nonce, a token that proves the form came from the site, prices the lines again and stores a private `order_request` record. A bot that fills in a hidden trap field gets the thank-you page and stores nothing.</Fact>
  <Fact k="Who can see it">Order requests and enquiries are private and left out of WordPress's public API, the address other programs use to read a site's content. The live site's list of content types shows neither.</Fact>
  <Fact k="What the buyer gets">The thank-you page reads 'Thank you, we have your order'. The site takes no payment and sends no email. The order request waits in the WordPress admin for someone to read.</Fact>
</Facts>
</Chapter>

<Chapter label="The catalogue" title="One catalogue file feeds both builds." lede="The product records behind that index come from one catalogue, content/catalogue.json, with 32 products, 8 categories and 2 collections. I built the whole shop as static HTML pages from it first. The WordPress seed, a script that fills the database, reads the same file, so both builds start from the same prices.">
<Facts>
  <Fact k="Static build">A Node.js script with no dependencies writes 63 HTML files and the search index. It refuses a page that lacks a path, a title, a description or a body, and any path that appears twice.</Fact>
  <Fact k="Seed">A PHP script of 1,092 lines reads the catalogue and fills WordPress. It stops with an error if the file is missing or empty.</Fact>
  <Fact k="Running it again">The seed looks each product up by its SKU and updates the one it finds instead of adding another. It uploads an image again only when the theme's image sizes change.</Fact>
  <Fact k="Same front end">The theme's 4 JavaScript files and its stylesheets are copies of the prototype's. A file comparison of the two folders finds no difference.</Fact>
  <Fact k="Platform">The site runs on Cloud Run, Google's service for running containers, from a WordPress image shared with five other sites. Each deploy updates the Cloud Run service, then runs the seed as a job and waits for it. If the seed fails, the deploy stops before it updates Firebase Hosting, which serves the public address. By then Cloud Run is already serving the new image.</Fact>
</Facts>
</Chapter>

<Chapter label="The limits" title="Where it stops today." lede="The seed fills a working shop, but Boxes is a demonstration, so it stops short of selling anything. A few gaps belong to the build itself, and I say what I would do about each.">
<List>
  <Item title="Nothing is sold.">There is no payment, no customer account and no stock count that goes down. The Trade account link leads to an application form. The thank-you page promises a reply by email, but the theme has no code that sends one. I would start by sending each order request to the shop's inbox.</Item>
  <Item title="The delivery and VAT rules live in two places.">The browser has £7.95, £150 and 20% written into its script, and the server reads them from the Shop settings. Change a setting and the basket would show a different total from the stored one. I would put those three figures in the JSON file the basket already loads.</Item>
  <Item title="The basket stays in one browser.">It does not follow a buyer from a laptop to a phone. That needs accounts.</Item>
  <Item title="No test checks that the two copies agree.">The repository has no tests and the deploy runs none. I would add one test that prices the same baskets in JavaScript and in PHP, so the two copies of the rule cannot drift apart unnoticed.</Item>
</List>
