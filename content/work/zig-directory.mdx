<Chapter label="Strategy" title="Help people find a site among DMOZ&apos;s three million links, however they ask." lede="Behind the pages on that board is one archive of DMOZ links. A directory is only worth keeping if people can find a site in it, and people ask in different ways. Some click down a tree of topics, some type a sentence, and some send an AI assistant to look. So the product has two jobs. It has to answer each of those well, and it has to keep every link safe in a database I built and run myself." split>
<Split reverse>
<Steps>
  <Step open name="The aim" hint="find a site, however you ask">Winning means a person looking for a site finds it in the directory, whether they walk down the topics, describe the site in a sentence or ask an AI assistant to look for them. DMOZSTYLE is my own product, built to serve those people and to run on a database I wrote myself in Zig.</Step>
  <Step name="Where to play" hint="visitors, assistants, submitters and admins">I built it for four kinds of user. Visitors browse fifteen topics, from Arts to World, down into 632,471 categories, or describe a site in their own words. Reading needs no account, and the reading pages load one script at most. AI assistants ask the same questions through MCP, the Model Context Protocol, a standard way for an assistant to call tools. Anyone who signs up can send in a link through a four-step form and follow it on their own dashboard. Admins approve or reject those links, and can edit, move or delete links and categories, one at a time or in bulk. Only an admin can change what visitors see.</Step>
  <Step name="How to win" hint="a sentence turned into filters">To answer a sentence, the search has to turn the sites, countries, religions, names and categories it recognises into filters the visitor can see and remove, and rank whatever is left well. I chose each part of the search by measuring it first, when the live directory held 91,995 links. I also keep facts about each link, such as the country it is tied to, beside the link itself, so the website and the assistants read the same facts. The cost is memory. Those facts and the search&apos;s own indexes are held in memory, and dmozdb already uses about 4.6 GiB of its 5 GiB limit.</Step>
  <Step name="What it takes" hint="my own database, in 5 GiB of memory">It takes a database that keeps every link it has confirmed, even through a power cut, and that fits in 5 GiB of memory on a small cluster I share with other projects. I built dmozdb in Zig for this one directory. It replies ok only once a write is on disk, and after a restart it reads its indexes back from a saved file. The cost is everything a general-purpose database already does. dmozdb has no query language, no transactions across records and no backup while it runs.</Step>
  <Step name="How we&apos;d know" hint="a number for each bet">Each bet has a number I can check. For the search it is recall at 10, the share of 300 test lookups whose link comes back in the first ten results, and the search built into dmozdb scored 0.907 when the live directory held 91,995 links. For speed it is the time a search spends inside the server, 96 ms at the median in one run of 12 fixed queries. For the database it is restart time, 47 seconds until it serves again. For assistants it is whether query_links, the tool that counts and groups links, agrees with an independent Python reference, and it did on all 19 test questions. There are no figures for visitors, so I can&apos;t say how many people use it.</Step>
</Steps>

<Chapter label="The engine" title="The server confirms writes once they're on disk." lede="That 18 GB store file is written by dmozdb, the database server I built in Zig for this directory. When it answers ok to a new link, that link has to survive a power cut. Waiting for the disk on every record made big imports crawl, so I changed where the wait happens.">
<DurableWrite />
<Split>
<Facts stacked>
  <Fact k="Storage">A store file of 16 KB pages arranged as B+Trees, sorted trees that find any record in a few page reads.</Fact>
  <Fact k="Log first">Every change goes first to the write-ahead log, a file where dmozdb adds each change to the end, with a checksum and a sequence number. Then dmozdb applies it to the trees.</Fact>
  <Fact k="One wait">Each write in a request notes its sequence and lets go of the write lock. Before the reply leaves, the request waits once for its last entry to reach the disk.</Fact>
  <Fact k="Shared sync">A background thread syncs every 2 ms, or sooner at 256 waiting entries, so one disk sync covers many requests.</Fact>
  <Fact k="Failure">If a sync fails, dmozdb stops the process before it replies, so after the restart it serves only what reached the disk.</Fact>
</Facts>
<List>
  <Item title="The old cost.">Each write waited for its own sync while it held the write lock. A 1,000-item import paid for 1,000 syncs, one after another.</Item>
  <Item title="Tested on a crash.">One test writes a link, drops the store without a clean shutdown, reopens it and checks the link comes back from the log. CI runs it on every pull request to main.</Item>
</List>
</Split>

<Chapter label="The ranking" title="How a search puts three million links in order." lede="When I chose hybrid, the live directory held 91,995 links. It now holds 3,042,241, 33 times as many, so every step had to stay quick at that size. On each search, the website turns the search query into an embedding. dmozdb then builds three shortlists of up to 200 links each. A short sum merges them into one order.">
<ZigRanking />
<List>
  <Item title="Why bge-small-en-v1.5.">[bge-small-en-v1.5](https://huggingface.co/BAAI/bge-small-en-v1.5) is a small embedding model from BAAI, trained for search. It was the model in the Python test that chose hybrid, so the scores I had measured were its scores. It runs inside the website on one processor thread. It embeds a search query in about 8 ms. Its embeddings have 384 dimensions. At one byte a dimension, three million links need over a gigabyte. A model with 768 dimensions would need twice that.</Item>
  <Item title="Checked before it shipped.">The website runs [an ONNX export](https://huggingface.co/Xenova/bge-small-en-v1.5) of the model, a 32 MB file pinned to one version, so it needs no Python. Its embeddings matched those of the model in the Python test at an average similarity of 0.996. Storing each dimension in one byte instead of four left every test score the same to three decimal places.</Item>
  <Item title="Three shortlists.">The keyword list takes the 200 links whose words match the search query best. The semantic list takes the 200 links whose embeddings are nearest to the search query's embedding. The category list finds the 3 categories whose names are semantically nearest to the search query, and scores the links filed under them. So a link can turn up through its category, even when its own text doesn't contain the words typed.</Item>
  <Item title="Reciprocal rank fusion merges by place.">The merge uses reciprocal rank fusion. It scores a link by its place in each list, not by its score. A keyword score and a semantic score can't be compared, so place is the only thing the lists share. A link gets 1 ÷ (60 + its place) from each list, and the scores are added. A link in tenth place on two lists scores 2 ÷ 70. That beats a link in first place on one list, at 1 ÷ 61. In the search on the right, nine of the ten links matched the keywords of the search query. Buddha Image Archive, in seventh place, came from the semantic list alone.</Item>
  <Item title="Keywords alone if the model is missing.">If the website can't embed the search query, dmozdb answers from the keyword list alone. It does the same when the store holds embeddings from a different model. A search never fails because of the model.</Item>
</List>

<List>
  <Item title="The slowest steps on the live site.">The category list is the slowest step, at 35 ms. It compares the search query with the names of all 632,000 or so categories. The semantic shortlist takes 25 ms, and turning the search query into an embedding takes 8 ms. The first two run inside dmozdb, the Zig engine, and the embedding runs in the website, the Deno server. A whole ranked search takes 96 ms inside dmozdb, so the category list and the semantic shortlist are 60 ms of it. These are median times on production.</Item>
  <Item title="No stale embeddings.">Embeddings always match the current text. Each embedding arrives with a fingerprint of the title and description it was made from. When dmozdb receives an embedding, it checks that the fingerprint still matches the link's current text. If the text has changed, dmozdb refuses the embedding. When a link's title or description is edited, dmozdb also deletes that link's old embedding. This prevents a link from being ranked using words that are no longer there.</Item>
</List>

<Chapter label="The rerank" title="An approximate score picks 200 links, then an exact score puts them in order." lede="Semantic search means comparing the search query with every link. At full size that is too much to read for each search. So dmozdb compares twice. An approximate comparison covers part of the store and keeps 200 links. An exact comparison then puts just those 200 in order.">
<ZigRerank />
<List>
  <Item title="TL;DR for search engineers.">Vector search is IVF-PQ over unit-length bge-small-en-v1.5 embeddings (384 dimensions, inner product): 256 lists, nprobe 32, and PQ at M = 96, 8 bits, on raw vectors rather than residuals, scored by ADC. The top 200 are then rescored against their 384-dimension int8 vectors, read from the store's B+Tree. Reciprocal rank fusion (k = 60, equal weights) merges three lists of up to 200: the reranked vector list, an OR keyword query scored by summed IDF, and every link in the subtrees of the three categories whose path embeddings are nearest the query, scored by the same ADC.</Item>
</List>
<List>
  <Item title="Why not compare everything exactly.">A link's full embedding is 384 bytes. The 3,042,241 of them come to about 1.2 GB. An exact search would have to read all of it. So dmozdb keeps the full embeddings in the store file on disk, and reads only the 200 it needs.</Item>
  <Item title="Product quantisation keeps a compressed vector in memory.">Product quantisation gives each link a compressed 384-dimension vector, 96 bytes long, held in memory. For the whole directory that is about 290 MB. It cuts the embedding into 96 sub-vectors of 4 dimensions. Each sub-vector position has a codebook of 256 centroids. Each sub-vector is replaced by one byte that names its closest centroid. The compressed vector is less precise than the original, but it is quick to score. ADC, asymmetric distance computation, scores the compressed vectors. It keeps the search query at full precision. Once per search, it builds a table that scores each sub-vector of the query against all 256 centroids in that position's codebook. A link's approximate score is then the sum of 96 table lookups, one for each byte of its compressed vector.</Item>
  <Item title="An inverted file index searches only the nearest clusters.">An inverted file index sorts the links into 256 clusters ahead of any search. Each cluster holds links with similar embeddings. It has a centroid, the central embedding of the cluster. A search compares the search query with the 256 centroids. It then scores only the links in the 32 nearest clusters.</Item>
  <Item title="Why the exact score is still needed.">Approximate scores are close but not exact, so two links with almost the same score can sit in the wrong order. The exact comparison scores the 200 again with their stored 384-byte vectors, one byte per dimension, and sorts them properly. It fixes the order of those 200. It can't bring back a link the approximate pass left out.</Item>
  <Item title="What it costs on the live site.">The approximate pass, the semantic shortlist, takes about 25 ms of a search. The 200 links then go to the merge in their exact order.</Item>
</List>
</Chapter>

<Chapter label="The ontology" title="What the directory knows about each link." lede="I dropped GraphRAG, but the questions it was meant to answer were still there. Hybrid search ranks links by keywords and by semantic search, yet it can't count the sites on one host or keep only the links tied to Japan. For that, dmozdb needs facts about each link. An ontology is the list of the kinds of fact it holds and how they connect. I keep them in a facts index in dmozdb's memory, worked out from each link's address, its place in the tree and its text.">
<ZigOntology />
<List>
  <Item title="One domain, many sites.">A site is the unit a person publishes, such as one Tripod member's pages. A host is the name at the front of an address, and a domain is the part someone registers. tripod.com is one domain spread over 17,475 hosts, 22,869 sites and 24,240 links, because members published under their own host name and under members.tripod.com/~name.</Item>
  <Item title="Three ways to a country.">A link is tied to a country by the ending of its address, such as .pk, by a category named for the country above it, or by a place its text names. Endings sold to anyone, such as .tv and .io, don't count. Places are matched against 36,465 place names, mostly from GeoNames, an open database of places, and 87 nationality words such as Japanese. Scored against 300 links that Claude labelled, 89% of the countries the index names are right, and it finds 75% of the ones there.</Item>
  <Item title="Names from a small model.">bert-base-NER, a small model trained to spot names in text, finds people and organisations, and a word list finds 11 religions from words such as mosque, church and gurdwara. On the same 300 links the religion list was never wrong, and about three in four of the organisations it named were right. Only 54% of the people were, though it missed almost no one. Qwen3-8B, a larger model, read countries better but was about 40 times slower for each link.</Item>
  <Item title="Start from the shortest list.">For each category, domain and name, the index keeps a sorted list of its links, so a question starts from the shortest list and never has to read every link. On the live store, half of these questions now finish within 4.3 ms, down from 604 ms when each one read every link.</Item>
</List>
</Chapter>

<Chapter label="Ask in a sentence" title="The search turns a sentence into filters you can see." lede="The facts index is what lets a visitor ask in plain words. The search page reads a sentence from left to right, takes the longest phrase it recognises as a site, a country, a religion, a category or a name, and turns each one into a chip, a small label above the results. Whatever words are left have to appear in the link. Nothing has to be typed in a special form, and removing a chip widens the search again.">
<ZigSentence />
<List>
  <Item title="Six kinds of chip.">A chip can name a site (On imdb.com), a country (Tied to Japan), a category (In Arts), a religion (About Buddhism), a person or organisation (Naming Benazir Bhutto) or a role (People filed as Politicians). Each one links to its typed form, such as site:imdb.com, for people who would rather write it.</Item>
  <Item title="Counts by country.">A search for jazz festival matches 319 links that hold both words, and the By country row splits them, 72 in the United States, 63 in France and 34 in the United Kingdom. Country is the only split so far.</Item>
  <Item title="Roles are a lookup.">Thirty-six role words, such as politicians, stand for the category names people are filed under, from Presidents to Prime Ministers and MPs. Roles aren't stored on links, so a role chip searches those categories wherever they sit in the tree.</Item>
</List>
<ZigNeighbours />
<List>
  <Item title="Similar sites.">A search for one site lists the sites filed in the same categories. A small category says more about two sites than a big one, so each shared category counts for less the more links it holds, and one with over 512 links is skipped.</Item>
  <Item title="Named alongside.">A search for a person or organisation lists the other names that appear on the same links, ranked by how many links they share.</Item>
  <Item title="See also.">Every category page ends with categories of the same name elsewhere in the tree, then the semantically nearest. A name repeated under every region, such as Education, gets no namesakes, because more than 24 categories share it.</Item>
  <Item title="Read from the same lists.">All three use the lists the facts index already keeps. On production they add 0 to 4 ms to a search for a site or a name, and about 38 ms to one for a category.</Item>
</List>

<Chapter label="Two front doors" title="The same directory for people and assistants." lede="An assistant gets those same answers through MCP. Its tools read the same dmozdb through the website's JSON API, so an assistant asking for sites like imdb.com gets the list a visitor sees. There are six tools, and only one of them, for ruling on submitted links, changes anything.">
<Split>
<Facts>
  <Fact k="Tools">browse_category, list_links, search_directory, query_links, find_related and review_submission, each one a whole task, such as browsing a category or reviewing a submission.</Fact>
  <Fact k="Counting">query_links counts, filters and groups links by site, host, domain, country, religion, person and organisation. It answered all 19 test questions the same way as an independent Python reference.</Fact>
  <Fact k="An answer">For Pakistan, query_links counts 1,735 links on 1,472 sites, whether the tie is a .pk address, a category named for Pakistan or a place in Pakistan named in the text.</Fact>
  <Fact k="Related">find_related gives an assistant the similar sites, the names named alongside and the related categories that the search page shows.</Fact>
</Facts>
<List>
  <Item title="Reading needs no account.">Any assistant can browse and search the way a visitor can.</Item>
  <Item title="Sign in to review submissions.">review_submission is for admins. Called without a token, it answers with a sign-in challenge, so the assistant can ask the user to sign in at that moment.</Item>
  <Item title="One set of accounts.">The website's own accounts act as the OAuth server that signs an assistant in, and the Python MCP service checks its tokens against keys the website publishes, so the two share no secret.</Item>
  <Item title="Checked twice.">The tool checks the role, and so does the API route behind it. A test in CI fails if a tool that writes is missing from the list of tools that need a sign-in.</Item>
</List>
</Split>

<Chapter label="Submissions" title="A new link goes live once an admin approves it." lede="Ruling on a submitted link is the one change an assistant can make, and it closes a short journey. Anyone with an account can send in a link through a four-step form. It is stored as pending, which visitors never see, and its embedding and facts are worked out the moment it arrives. It goes live only when an admin approves it.">
<ZigLifecycle />
<List>
  <Item title="Three ways to rule.">An admin can rule from the admin pages, where a bulk bar approves, rejects, moves or deletes up to 200 links at once, from the JSON API with an admin's token, or from an assistant through review_submission.</Item>
  <Item title="A ruling can be undone.">A link can move from any state to any other, so an approved link can be rejected later and a rejected one approved.</Item>
  <Item title="Duplicates turned away.">A link whose address is already in the directory is refused before it is stored. A bloom filter, a small test in memory that can prove an address is new, answers first, and an index of address hashes settles the rest.</Item>
  <Item title="The domain's standing.">When an assistant rules, the reply adds what the directory already holds from that domain. For imdb.com that is 10,832 approved links in 10,656 categories.</Item>
</List>
</Chapter>

<Chapter label="The limits" title="Where the strategy is not proven yet." lede="Once approved, a link reaches visitors through everything above, and parts of it fall short today. The search scores date from when the directory held 91,995 links, the facts carry the mistakes of the model that found them, and a few pages on the live site say things that aren't true. I also built dmozdb to serve one directory and nothing else. Each limit below is set against the part of the strategy it puts at risk.">
<List>
  <Item title="How we&apos;d know: search quality was measured on 91,995 links.">The live store now holds 3,042,241. A check against the live site in October found the right link in the top 10 for 92% of searches by a person's name and 40% of searches by topic. I would run the whole test set against the live store next.</Item>
  <Item title="How to win: keywords must match as typed.">dmozdb has no phrase search and no allowance for typing mistakes, and it doesn't lowercase accented letters, so blüm won't find Blüm.</Item>
  <Item title="How to win: the facts are noisy.">Only about half the names the model calls people are people, so ordinary words turn up beside real names. A search for biographies of politicians puts card-game pages first, because Games also has a category called Presidents.</Item>
  <Item title="What it takes: saving the indexes pauses writes.">The file that makes a restart quick is saved every hour (1.17 GB when I first measured it). Each save takes 46 to 48 seconds, and new writes wait while each part is written.</Item>
  <Item title="What it takes: dmozdb is built for one directory.">It has no query language, no transactions across records, one writing process and no backup while it runs. The wire protocol has no encryption, so the server listens only to its own machine unless told to trust a network, and on the cluster it trusts the cluster's private one.</Item>
  <Item title="What it takes: totals across every link aren't safe yet.">A count over all three million links with no filter crashed production on 19 November 2026. I fixed the cause but haven't run that query on production since, so the directory can't yet say how many sites or people it holds in total.</Item>
  <Item title="Where to play: some pages say the wrong thing.">The home and about pages say sixteen categories and list fifteen. Every imported link shows the same Added date, the day of the import. The home page's Cache pages counter shows every page in the store file.</Item>
  <Item title="Where to play: two pieces aren't finished.">The editor role exists but gives no rights beyond a normal account, and only an assistant's reply shows a domain's standing. The admin pages don't show it yet.</Item>
</List>
</Chapter>

An assistant asking through MCP gets the same answer from the same store, and a new link reaches both once an admin approves it. These three choices did most of that work.">
