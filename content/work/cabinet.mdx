<Chapter label="Isolation" title="Every query belongs to one workspace." lede="Those pages, entries and tokens share their MySQL tables with every other workspace. A single query that forgot to filter by workspace would show one shop another shop's drafts. I wrote the filter once, in the model layer that every database read and save goes through, so the code that answers a request can't leave it out.">
<WorkspaceFence />
<Facts>
  <Fact k="Reads">Cabinet is built on CakePHP, a PHP framework. A CakePHP behaviour (code the framework runs on every find and save for a table) called `TenantBehavior` adds a filter for the active workspace to every find on 19 tables.</Fact>
  <Fact k="Writes">A new row takes the active workspace. Saving a row that belongs to another workspace stops with the error ‘Refusing to persist a row owned by another workspace.’</Fact>
  <Fact k="No workspace">If nothing has set a workspace, the query stops with an error instead of returning every shop's rows, so a mistake fails closed.</Fact>
  <Fact k="Who sets it">The first part of the URL sets the workspace for each web request. An unknown workspace gets a 404, and a signed-in user from outside it gets a 403 on its admin pages.</Fact>
  <Fact k="Addresses">Page addresses (slugs) are unique within a workspace, so two shops can each have an /about page.</Fact>
  <Fact k="Migration">Cabinet began as one site. One migration (a script that changes the database) added `workspace_id` to 15 tables, a second moved the existing rows into a default workspace, and a third made the column required.</Fact>
</Facts>
<List>
  <Item title="Tested from both sides.">16 tests in 3 files cover the rule. Nine use a second workspace: they try to read its rows, point a page, comment or menu item at its pages, or save a row stamped with its id. One clears the workspace and expects the query to fail.</Item>
  <Item title="The API too.">Three GraphQL tests check that one workspace's post does not appear on another workspace's endpoint, that a token for one workspace is refused on another's, and that a write token cannot change another workspace's post.</Item>
</List>

<Facts>
  <Fact k="Save">Cabinet reads the block ids out of the page body and rewrites that page's rows in a `page_blocks` table in one all-or-nothing database transaction, so it knows which pages use which block.</Fact>
  <Fact k="Render">Each placeholder becomes escaped HTML that suits its kind: a callout becomes an `aside`. A reference to a deleted or unknown block renders nothing.</Fact>
  <Fact k="Delete">A delete rule checks `page_blocks` and refuses to delete a block a page still uses, with a foreign key in the database (a rule that ties each use to its block) behind it. The admin says ‘This block is in use on one or more pages and cannot be deleted.’</Fact>
  <Fact k="Safety">Cabinet passes rich text through HTMLPurifier on save, a library that keeps only allowed tags, and the placeholder's id must be a number. A call to action with an unsafe link renders without the link.</Fact>
  <Fact k="Kinds">Six: callout, quote, statistic, call to action, image and file.</Fact>
</Facts>

<Chapter label="Content as code" title="Pages that live in version control." lede="A block lives in one place in the database. Cabinet can also keep pages, posts and collection entries as plain text files (YAML) in version control, for CI (the checks that run on every change) to import. An import that CI runs again and again has to change nothing when nothing has changed.">
<Facts>
  <Fact k="Export">`bin/cake content_export` writes a workspace's content to `content/{workspace}/`. Collection schemas live as files in `config/collections/`, and `bin/cake schema_import` loads them.</Fact>
  <Fact k="Hash gate">Import takes a SHA-256 hash of each file, a fingerprint of its text, and skips the file when the hash matches the last import. `--force` ignores the gate.</Fact>
  <Fact k="Scope">Import runs inside the one workspace named by `--workspace`, so the isolation rule covers every row it writes.</Fact>
  <Fact k="Bad files">A file that fails becomes a failed result. The rest of the run carries on, and the command exits with an error.</Fact>
  <Fact k="CI proof">On every pull request and every push to main, the Content Sync workflow builds a fresh MySQL 8.4 database, imports the committed files, then imports them again. The job fails unless the second run reports 0 created, 0 updated, at least 1 skipped and 0 failed.</Fact>
</Facts>
</Chapter>

<Chapter label="The limits" title="Where it stops today." lede="The workspace rule covers every find and save on 19 tables. These are the places where Cabinet still relies on code that remembers the workspace by hand, or on running as one server.">
<List>
  <Item title="The scheduler runs outside any workspace.">The cron command that publishes scheduled pages looks them up without choosing a workspace first, so the rule stops it with an error and nothing publishes. Its 2 tests pass because the test setup starts every test inside workspace 1. I would run it once per workspace, as the import does, and cover posts and entries, which have a scheduled state but no command.</Item>
  <Item title="Bulk changes name the workspace by hand.">CakePHP runs the rule on finds and saves, but not on bulk updates and deletes. Each of the 9 bulk calls in the code adds the workspace to its own conditions, and a new one that forgot could change another shop's rows.</Item>
  <Item title="Each admin action checks its own permissions.">Admin actions call their policies (the rules for who may do what) themselves, and the framework's check that each action did so is switched off. A new action that forgot would not be caught. I would switch that check on.</Item>
  <Item title="The code assumes one server.">Sessions, caches and the rate limiter's counters default to files on the server's own disk. The README names Redis or APCu for the cache when there is more than one server.</Item>
</List>
</Chapter>

<Chapter label="The learning" title="What carried forward." lede="Every shop's content sits in one database, so each shop's privacy rests on one rule and on the few places that rule does not reach.">
<Split>
<List>
  <Item title="Put the rule where nothing can skip it.">A workspace filter in the code behind each request would rely on every one of them getting it right. One behaviour on 19 tables takes that chance away for finds and saves, and the 9 bulk calls show what is still left to code by hand.</Item>
  <Item title="Make the unsafe case an error.">With no workspace set, a query stops with an error, so a job that forgets its workspace stops instead of reading across shops. The scheduler is such a job, and its tests missed it because each one starts inside a workspace. Tests should start with no workspace, as production does.</Item>
  <Item title="Prove a repeatable job by repeating it.">CI runs the import twice, and the second run has to change nothing.</Item>
</List>
