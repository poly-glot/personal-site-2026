<Facts>
  <Fact k="Model">A case study is a set of fields written in a YAML file, a plain text format. The shared platform's yacf plugin reads the file and builds the edit screen in the WordPress admin.</Fact>
  <Fact k="Place">A region chosen from five (Africa, Asia, Europe, Latin America and the Middle East), coordinates written as text, such as 4.71° N · 74.07° W, and a line naming the client.</Fact>
  <Fact k="Results">A list of figures, each with a label. The sample Bogotá study says '3 corrections published'. Like every result on the site, it is written copy and measures nothing.</Fact>
  <Fact k="Services">Links to the service pages. The template writes the services line from their titles, so renaming a service updates every case study that uses it.</Fact>
  <Fact k="Chapters">The challenge, Our approach and The outcome are three rich-text fields. The template leaves out any that is empty, so a short study needs no layout of its own.</Fact>
  <Fact k="Next">The Next case study link follows the order an editor sets, and wraps from the last study to the first.</Fact>
</Facts>

<Chapter label="The front end" title="One stylesheet and two small scripts." lede="Those places reach a visitor through the carousel on the home page and long pages of photographs. I kept the code a browser downloads for them small: one stylesheet, and 2,499 bytes of JavaScript that adds controls to pages that already work without it.">
<Figures>
  <Figure wide src="/img/work/parley/service-faq.webp" w={1600} h={1000} alt="The heading Questions we're often asked, with the question Will our conversation be confidential? open and answered, above two closed questions." title="The questions">Open a question to read the answer. Each one is the browser's own open and close element, with no script behind it.</Figure>
</Figures>
<Facts>
  <Fact k="41 files">The theme's CSS is 41 small files, one per piece of the page: 3 for the base, 6 for small parts such as the logo, and 32 for components. Together they hold 2,738 lines.</Fact>
  <Fact k="One file">One shell command joins the 41 files in a fixed order into `main.css` as Docker builds the server image. The repository ignores that file and keeps only the sources.</Fact>
  <Fact k="Before and after">The commit that made the change says the page went from 41 render-blocking requests (files the browser must finish before drawing anything), 20.3 KB compressed, to 1 request of 8.8 KB. The live file today is 55,748 bytes, and the server sends it compressed as 9,998 bytes.</Fact>
  <Fact k="Local setup">If `main.css` is missing, the theme loads the 41 files one by one in the same order, so the local development setup runs without a build step.</Fact>
  <Fact k="Scripts">The menu script (679 bytes) loads on every page and the carousel script (1,820 bytes) on the home page only. Both wait until the browser has read the page, so neither holds it up while it loads.</Fact>
  <Fact k="Without them">On a screen narrower than 1,024 pixels the menu links sit in a row under the logo, and each carousel on the home page scrolls sideways and stops on each slide. The menu script shows a menu button, and pressing Escape closes the menu and puts focus back on the button. The carousel script adds the dots and arrows.</Fact>
</Facts>
</Chapter>

Parley promises every conversation is confidential, so the form saves each message as a private record inside WordPress instead of passing it to an outside form service.">

<List>
  <Item title="A private record.">Each message becomes an enquiry, a content type that stays off the public site. The admin lists enquiries with the email and the topic in their own columns.</Item>
  <Item title="Plain HTML first.">The form posts to WordPress's own handler, and the thank-you is the contact page with `?sent=1` on the address. The browser checks the required fields and marks a field red only after the visitor has tried it.</Item>
  <Item title="Checked on the server.">A one-time token from WordPress, called a nonce, shows the post came from this form. The handler cleans every field before saving it, and saves nothing without a name, an email and a message.</Item>
  <Item title="A trap for bots.">A hidden field called website stays empty for people. A bot that fills it lands on the same thank-you page as everyone else, so it cannot tell that the handler threw its message away.</Item>
  <Item title="The crisis line.">The 24-hour number on the contact page and in the footer is a link that starts a call on a phone. Both read the same two fields in Site settings, the number as shown and the number to dial, so an editor changes it in one place.</Item>
</List>
</Chapter>

<Chapter label="The platform" title="One seed fills the site on each deploy." lede="The contact page that holds the form reaches production the way every page, service and case study does: through one seed, a PHP file that writes the site's content and is safe to run again. Parley shares its server image and the yacf plugin with five other client sites. The theme, the model and the seed belong to this repository.">
<Facts>
  <Fact k="Seed">One file of 968 lines writes 8 pages, 7 services, 5 case studies, 6 team profiles, 9 posts, 4 menus, the site settings and 23 images, then deletes WordPress's sample content.</Fact>
  <Fact k="Safe to rerun">It finds each post by its slug, the last part of its address, and updates it if it exists. It tags each image so a rerun does not upload it twice, and fills a menu only when the menu is empty.</Fact>
  <Fact k="On each deploy">GitHub Actions builds the image and deploys it to Cloud Run, Google's service for running containers, then runs the seed as a job and waits for it. If the job fails, the run stops before it updates Firebase Hosting, which serves the public address. By then Cloud Run is already serving the new image.</Fact>
  <Fact k="Why">The first deploys left the seed job as a manual step. I added it to the pipeline so seeded content and images, including the team portraits, reach production without one.</Fact>
</Facts>
</Chapter>

<Chapter label="The limits" title="Where it stops today." lede="Parley is a demonstration, so the phone number and the legal pages are placeholders, and the newsletter form in the footer goes nowhere. The gaps that belong to the build start with the enquiry form and the seed.">
<List>
  <Item title="Nobody hears about an enquiry.">The handler sends no email, so someone has to open the Enquiries list in the admin. An agency that promises a reply within one working day needs a notification for each new record, and that is the first thing I would add.</Item>
  <Item title="The seed undoes admin edits.">Each deploy rewrites the seeded pages, posts and settings, so a change made in the admin, such as a new crisis line number, lasts until the next push. Menus are the exception. I would change the seed to write content only when it is missing.</Item>
  <Item title="A rejected form says nothing.">If the name, email or message reaches the server empty, the handler sends the visitor back to the form with no error. Only the browser checks the consent box. I would have the handler say what is missing and check consent too.</Item>
  <Item title="The home page clips on a phone.">At 390 pixels wide the second line of the headline, Win the argument, loses its last letter, because the CSS stops the line from wrapping. I would let it wrap or scale the type with the screen.</Item>
  <Item title="Nothing checks the build.">The repository has no tests, and the deploy runs no page or accessibility checks. The live pages send no content security policy, the header that tells a browser which scripts it may run. I would add a page check after the seed runs, and set the headers in the Firebase Hosting config.</Item>
</List>
</Chapter>
