## The problem {#the-symptom}

QA told us the asset dashboard felt heavy for customers with large catalogues.
When we looked, it was worse than heavy. The first load took 30 seconds, the
network panel filled up, and Chrome tabs sometimes crashed.

We hadn't seen any of it ourselves, because our test accounts had small
catalogues. It only showed up for the customers at the top of the list.

## The cause {#the-diagnosis}

Each card on the dashboard used a hook to keep its asset up to date. The hook
opened a websocket when the card appeared and closed it when the card went
away. It looked something like this:

```jsx
function useAssetUpdates(id) {
  const [asset, setAsset] = useState(null);

  useEffect(() => {
    const socket = new WebSocket(`${UPDATES_URL}/${id}`);
    socket.onmessage = (event) => setAsset(JSON.parse(event.data));

    return () => socket.close();
  }, [id]);

  return asset;
}
```

On its own, that's tidy React. The trouble is how many copies run at once. With
600 cards on the page, the browser tried to open 600 connections in the first
second. The server would have accepted them all, but browsers cap how many
websockets can be open at once, and 600 is well past that cap.

## What didn't work: throttling {#the-wrong-fix}

Our first idea was to open the connections more slowly. We wrote a `useThrottle`
hook that opened a few connections on each frame instead of all of them at
once.

The page did load sooner. But updates now arrived late, and the browser worked
harder than before, because it was also running the scheduler that spaced the
connections out. And the page still opened 600 connections. We had only spread
them out.

## What worked: one shared connection {#the-right-fix}

The real fix was to move the connection out of the cards. The dashboard keeps
one websocket and a small registry: a list of which card wants updates for
which asset. When an update arrives, the registry stores it and tells only the
cards watching that asset. The examples below use React 19.

```js
export function createSubscriptions(url) {
  const latest = new Map();
  const listeners = new Map();
  let socket = null;

  function connect() {
    socket = new WebSocket(url);
    socket.onmessage = (event) => {
      const { id, value } = JSON.parse(event.data);
      latest.set(id, value);
      listeners.get(id)?.forEach((notify) => notify());
    };
  }

  function subscribe(id, notify) {
    if (!socket) connect();

    const forAsset = listeners.get(id) ?? new Set();
    forAsset.add(notify);
    listeners.set(id, forAsset);

    return () => {
      forAsset.delete(notify);
      if (forAsset.size === 0) listeners.delete(id);
      if (listeners.size > 0) return;

      socket.close();
      socket = null;
    };
  }

  return { get: (id) => latest.get(id), subscribe };
}
```

The socket opens when the first card subscribes and closes when the last one
leaves. Creating the registry does nothing on its own, so it's safe for React to
create it during render, even twice in Strict Mode.

The dashboard creates the registry once and shares it through context. In React
19 the context itself is the provider:

```jsx
const SubscriptionsContext = createContext(null);

function Dashboard({ assets }) {
  const [subscriptions] = useState(() => createSubscriptions(UPDATES_URL));

  return (
    <SubscriptionsContext value={subscriptions}>
      {assets.map((asset) => <AssetCard key={asset.id} id={asset.id} />)}
    </SubscriptionsContext>
  );
}
```

Each card reads its asset with a hook we called `useResource`. It uses
`useSyncExternalStore`, React's own hook for data that lives outside React.
React handles subscribing and unsubscribing, and every card sees the same
version of the data in a render, which copying values into state from an effect
doesn't guarantee.

```jsx
function useResource(id) {
  const subscriptions = use(SubscriptionsContext);

  const subscribe = useCallback(
    (notify) => subscriptions.subscribe(id, notify),
    [subscriptions, id],
  );

  return useSyncExternalStore(subscribe, () => subscriptions.get(id));
}
```

`subscribe` is wrapped in `useCallback` because React subscribes again whenever
it gets a new function. The snapshot is the stored value, which only changes
when an update arrives, so cards don't re-render for nothing.

This is a sketch. In production the registry also tells the server which assets
it wants, and reconnects with a backoff if the connection drops.

The dashboard now opens one connection. CPU use is low, the network panel is
quiet, and the tab crashes stopped. A 601st card makes no difference, because
cards no longer connect to anything themselves.

## The rule we use now {#hook-budgets}

A hook looks free because it's one line in a component. But anything it sets
up, like a connection, a timer or an event listener, is paid for once for every
copy on the page. With 600 copies, a small cost becomes the reason the page
falls over.

So in code review we now ask one question: how many of these will be on the
page at the busiest moment? If the answer is more than about 50, the setup
doesn't belong in the per-card hook. It moves up to the parent, and the cards
subscribe to it.

## A checklist for hooks {#what-i-tell-juniors}

<Checklist>

- For data that lives outside React, like a socket, read it with
  `useSyncExternalStore` instead of copying it into state from an effect.
- If a hook opens a connection, ask how many other copies will open one too.
- If you're spacing connections out to cope, move the connection up to the
  parent instead.
- If most cards are off screen, only render the visible ones. Fewer cards means
  fewer subscriptions of every kind.

</Checklist>

## In short {#closing}

Hooks make each component easy to reason about on its own, and that makes the
total cost easy to miss. Count the copies before you put setup inside one.
