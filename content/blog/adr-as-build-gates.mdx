[HookLab](https://hooklab.junaid.guru/) ([Case Study](/work/hooklab/)) is a tool
I built for developers to receive webhooks, the automatic messages one service
sends another. Its README says a guest can create three endpoints, which are the
addresses that receive them. The database's access rule, which enforces the
limit, lets a guest create ten. On 6 April I raised the limit, and in the same
commit I changed the rule, the browser code and the test that checks the rule. I
didn't touch the README. No test failed and no tool warned me, so the README
still says three.

The reasons behind a limit like that are what an architecture decision record,
or ADR, is for. Michael Nygard [proposed the format in
2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions):
a short file in the repository that gives a decision, the context behind it, its
status and its consequences. When a decision changes, the old record stays,
marked as superseded by a new one, so the history of why remains readable, and
[adr.github.io](https://adr.github.io/) collects templates and tools for writing
them. The point is that whoever finds the code later can see why it is the way
it is, so they don't have to accept it blindly or change it blindly.

The guest limit had no ADR, though, because I don't keep separate ADR files. My
decisions live in whatever documentation each project already has.
[OpenGuessr](https://openguessr.junaid.guru/) ([Case Study](/work/openguessr/))
has a Design Decisions section in its README with nine entries, this site keeps
its decisions in rules files, and my platform repository,
[firebase-cloud](https://github.com/poly-glot/firebase-cloud), keeps them in its
docs. Unlike an ADR, those describe the code as it is now, so they go wrong when
the code changes and nobody edits them. That is what happened to HookLab's
README.

## Which of my decisions stayed true {#which-stayed-true}

To see how far that had gone, I went back through four of my projects and asked
one question of every decision I found: if somebody broke this tomorrow, what
would tell them? Some of the answers are tests of a database's access rules,
which try an action as a particular user and expect the database to refuse it.
One is a hook: a script that runs by itself each time my coding assistant edits
a file. The first panel below holds four decisions that something checks, and
the second holds four that nothing does. These eight are the clearest examples,
not a full count.

Every decision in the second panel was already wrong or broken when I looked.
The first is the guest limit. The OpenGuessr README promises that upcoming
answers stay hidden, but every player can read them, which I [wrote
up](/blog/openguessr-fair-play/) separately, and the one test that looks at the
promise runs on a sample game whose unrevealed round has no answer in it, so it
passes. The [firebase-cloud
docs](https://github.com/poly-glot/firebase-cloud/blob/main/terraform.md#cloud-functions-codebase-isolation)
say every app must declare a codebase, a name that stops one app's deploy
deleting another app's functions, and OpenGuessr, which runs on firebase-cloud,
doesn't declare one. And the firebase-cloud README lists eight of its modules,
where the repository has 12.

Each decision in the first panel has a check behind it that fails when the
decision breaks, and I found no sign that any of them had drifted. A check only
helps if something runs it, though. HookLab's rules tests run only when I start
them on my laptop, and the automatic checks that run on every push leave them
out.

## The guest limit, written in four places {#four-places}

Even when I run them, the rules tests check only one of the places the guest
limit is written. The number lives in the database rule, the test, the browser
code and the README. I changed the first three in one commit. The README is the
one place no test or tool reads, so I missed it.

The limit started at three. HookLab gives every new guest six demo endpoints, so
under the old limit every guest was already over it and got a permission error
on their first endpoint of their own. The
[fix](https://github.com/poly-glot/hooklab/commit/6418dec84a4242bd3aea1b3a1d9904d195c03762)
raised the limit to ten: six demo endpoints and four of the guest's own. That
reasoning is what an ADR would have kept. The README needs a different fix: stop
repeating the number and point at the rule, or add a test that fails when the
README and the rule disagree.

## Two small checks {#two-small-checks}

The rules test that guards the limit is what Thoughtworks calls an
[architectural fitness
function](https://www.thoughtworks.com/insights/articles/fitness-function-driven-development):
a test of how close a system is to an architectural aim. Fitness functions don't
have to be big, and two small ones of mine show what makes one useful. The first
is in firebase-cloud, which sets up the cloud services for my apps with
Terraform, a tool that reads files describing the services and creates them. If
a secret was missing, Terraform received an empty string and would have saved it
as an empty signing key, the secret one of my apps signs its output with. The
[fix](https://github.com/poly-glot/firebase-cloud/commit/76ab5f96a2b48f03e1eda7d25d7fb0c46f8ce62e)
is a `validation` block, which refuses to continue unless the secret looks like
a private key:

```hcl
validation {
  condition     = startswith(trimspace(var.c2pa_demo_signer_key), "-----BEGIN PRIVATE KEY-----")
  error_message = "c2pa_demo_signer_key must be a PKCS#8 PEM private key; set the C2PA_DEMO_SIGNER_KEY GitHub secret to cert/claim-signer.key from c2pa-demo."
}
```

The condition checks that the secret starts with the header line of this kind of
private key file. It fails early, before anything changes, and the message names
the secret to fill in, so I, or anyone else who hits it, can fix it without
digging through the code. Terraform documents [the same idea for any input
variable](https://developer.hashicorp.com/terraform/language/validate).

The second is the hook from the first panel. It enforces this site's rule that
components don't use inline styles, and with the messages shortened it comes
down to this (the [full
script](https://github.com/poly-glot/personal-site-2026/blob/a0a9ca0aaa5be6083cf58c5f416e1fc68764aeae/.claude/hooks/web-guard.mjs)
is in the repository):

```js
if (resolved.endsWith(".tsx") && INLINE_STYLE.test(content)) {
  console.error(`web-guard: inline style in ${rel}`);
  process.exit(2);
}

if (resolved.endsWith(".module.css") && RAW_BLEED.test(content)) {
  console.log(`web-guard (warning): raw 100vw in ${rel}`);
}

process.exit(0);
```

An inline style is always wrong here, so the script exits with code 2, and my
coding assistant gets the message back as an error to fix before it carries on.
A raw `100vw` in a stylesheet is only sometimes wrong, because the pattern can
also match harmless CSS, so the script prints a warning and exits normally. Both
messages say what to do instead and point to the rule. The script only sees my
assistant's edits, so a style attribute I typed by hand would get past it.

## Decisions I would not check {#not-everything}

Checks like these take work and still have gaps, so not every decision gets one.
The OpenGuessr README explains why the game is plain JavaScript with Lit web
components instead of a framework, and why the host, not a timer, moves the game
from one round to the next. A test could catch either one changing, but neither
would change by accident. The record is still worth keeping, because it answers
"why is it like this?" for the next person, and the next person is often me.

The decisions I would check are the ones that are easy to break by accident,
costly when they break, and easy for a script to read, such as a number or a
permission. A guest limit fits all three, and so do the rules that stop a player
writing their own score. My preference for plain JavaScript is easy for a script
to read but hard to break by accident, so it stays a written note.

## Try it on one decision {#closing}

Pick one number or permission that a README of yours promises, and either point
the README at the code that enforces it or write a test that fails when the two
disagree. I found four to fix. The codebase setting in OpenGuessr comes first,
because leaving it out can delete another app's functions. HookLab's README
should point at the rule instead of repeating the limit, and its rules tests
should run with the automatic checks on every push. The OpenGuessr promise needs
a test that fails while any player can read an upcoming answer, and the
firebase-cloud README needs its module list brought up to date.
