My first WordPress site needed five changes to its setup on my platform in its
first week. The six WordPress sites I built after it needed one between them.

The platform is [firebase-cloud](https://github.com/poly-glot/firebase-cloud),
the repository that sets up the cloud side of my apps. Each app has one setup
file in it, written in Terraform, a tool that reads files describing cloud
services and creates them. The file says what the app needs from the platform,
and after that the app's own repository publishes new versions by itself. I
count a change as a commit, a saved edit in git, to that file. I am the only
maintainer, and every app on it is mine, including this site.

## Counting what the platform holds {#receipts}

The easy way to describe a platform is by what it holds, and that is how
firebase-cloud's README does it: it lists the modules, which are reusable
building blocks such as a hosting site or a database. Today there are 12
modules, 29 apps and 167 commits since 29 March. Those numbers show how much I
have built, but not whether the next app got easier to set up than the last. The
Cloud Native Computing Foundation's (CNCF) [white paper on
platforms](https://tag-app-delivery.cncf.io/whitepapers/platforms/) says the
success of an organisation's products and applications is the true measure of a
platform's success, and among its efficiency measures it lists the time to build
and deploy a brand-new service. Evan Bottcher's
[definition](https://martinfowler.com/articles/talk-about-platforms.html) points
the same way: a platform is a set of self-service tools and services, run as an
internal product, that lets delivery teams deliver faster with less
co-ordination.

## Counting each app's first week {#first-week}

Both of those judge a platform by the people using it, so for every app I took
two numbers from the git history on 15 November. The first is how many times its
setup file changed in the app's first week, meaning commits within seven days of
the one that added it. That is roughly how often I had to go back to the
platform for the app after day one, whether the platform lacked something or I
had set the app up wrong. The second is how many lines the file has today, which
is roughly how much I have to write for each app. Both panels list the apps in
the order they were added.

Most apps needed little: 24 of the 29 needed two changes or fewer, and 13 needed
none. The other five needed three or more, and they account for nearly two
thirds of the 45 changes: [HookLab](https://hooklab.junaid.guru/) ([Case
Study](/work/hooklab/)) with twelve, OpenGuessr and my first WordPress site with
five each, Azadi with four and Shehryar with three. HookLab was the first app on
the platform. Its twelve covered who could access what, the app's settings, a
database name and where its AI model runs, and some of them were me building the
platform itself.

## The six WordPress sites {#wordpress}

The clearest case is my first WordPress site, `wordpress-sample`, which needed
five changes in its first week: three changes to how it kept uploaded files, a
schedule for WordPress's background jobs, and a change to how the platform
checks that the site has started. The day after I added it, I wrote a [module
and a
template](https://github.com/poly-glot/firebase-cloud/commit/eedbffab632107edabb068dce1469040034da054)
for WordPress sites. The template is a starter file that I copy and fill in for
each new site.

Each of the six sites I built with the template has a file of 39 to 44 lines,
against 197 for my first WordPress site. Those few lines give a site its own
database, storage for uploads, web server, schedule for background jobs and web
address. The six needed one change to their own files in their first weeks. I
changed the module three more times after writing it, and those changes count
against none of the six, so they cost me a little more than their numbers say.

## Where the counts fall short {#limits}

These counts are rough. A commit is not a unit of effort: four of OpenGuessr's
five changes were permission fixes made on one day, and one of Azadi's four only
tidied spacing. Apps differ too, and a WordPress site was always going to be a
smaller job than an app with custom server code and access rules. The line
counts are today's, after later changes, so they overstate what an app needed on
day one. I can't prove that the template is the reason the six needed so little.

The bigger gap is that I am the only user, so the only complaints are mine. A
platform team serving other teams would hear about things a git history can't
show: how long a team waited, which workarounds it built, whether it gave up on
the platform. Its platform may not have a file per app either, so I would count
something that tells the same story: the requests a new team raises with the
platform team in its first week. I would start with the history because it is
free to read, and then ask the teams what it misses.

## Try it on your own platform {#closing}

Count those first-week requests and chart them by team, in the order the teams
joined. In a company, each of those requests is a team waiting on the platform
team, which is the kind of dependency [Team
Topologies](https://teamtopologies.com/key-concepts) warns about: a good
platform should make teams "move faster, not generate more dependencies to
manage". If the same kind of app keeps needing the same changes, build a module
for that kind next. I put what my first WordPress site's five changes taught me
into the WordPress module, and the six sites built on it needed one change
between them.
